### 分类统一

以前功能页和设置侧栏各有一套分类，互不相同。现在是一套：

```

```

### 名字只有一个来源

```
FeatureGroup.title      8 个组名
AppFeature.name         57 个功能名
SettingsPage.title      每个页的标题
```

六类消费者（功能页、侧栏、快捷键页、引导页、命令栏、菜单面板）全走这三个入口。
以前有 98 处直接读字符串，现在是 0，护栏挡着，允许清单是空的。
单功能页的标题就是那个功能的名字，页不再有自己的名字。

### 可安装的单位从「功能」改成「页」

以前 57 个功能各自装卸，小到「反转滚动」都要单独装。现在按页装卸（31 个单位），页里每个成员一个开关。
开关关掉 = 以前的卸载：服务不启动，事件监听不装，定时器不跑。开销一分不多。

### 拆页

通用页解散，快捷面板解散，切换器拆出 Dock，能源拆四页，声音拆三页，鼠标拆出触控板。

### 字符串

6 个功能的文案从 953 字段的单体搬进各自的结构体；73 个没有任何读取者的字段删掉（每个都白翻译了 13 种语言）。

### 简体术语

```
三指中键        原「中键点按」——以后可能追加别的三指行为
窗口切换器      原「App 切换器」——它也在同一个 App 的多个窗口间切换
Dock            保留英文，和 App 同一条规则
```

### 迁移

老用户的可用性数据、拆开的预览设置键、旧版本的备份导入，都有一次性迁移。

## Planned

### 语言

**官方 6 种：英 / 简中 / 德 / 法 / 西 / 日。**

**回落机制已完成**（`refactor(l10n)`，净 −2210 行）。做法是把英文搬进声明当默认值：

```
以前   struct Strings { let menuQuit: String }      13 份字面量，每份必须填满
       static let enUS = Strings(menuQuit: "Quit Vorssaint", …)

现在   struct Strings { var menuQuit: String = "Quit Vorssaint" }
       static let enUS = Strings()                  英文就是声明本身
       static let de   = Strings(menuQuit: "Vorssaint beenden", …)   缺的自动读英文
```

44 个字符串结构体、2261 个字段都是这样。**加一个字段现在只写英文一处**，另外 12 份字面量不用动也照样编译。
调用点一个没改，编译时间没变（280 → 282 秒）。

**只有英文是必填的**，而且它必填是因为它就是那些默认值，写不漏。其余 12 种随意，翻多少算多少。

简体保留熟悉的英文原词（App、Dock）。唯一例外是「桌面与程序坞」——那是苹果系统设置面板的官方名字，用户要照着去点。

### 界面

所见即所得，优化视觉与动画。功能页去掉套装（去掉时注意：引导里要做到勾选即启用，否则用户勾完发现功能不动）。

**「监视」改成「监控」，「系统监视器」改成「系统监控」。** 监视读起来像在盯着人，监控才是这类功能的常用叫法。

要改的 6 处（简体，`grep 监视` 共 8 处）：功能页分组名「系统监视器」、侧边栏页名「监视」、功能页那句「全部关闭后，监视器会…」、两条套装说明、关于页的一句话，以及「正在监视下载文件夹」「无法监视鼠标」这两条动词。**「活动监视器」不改**——那是苹果自己 App 的名字，用户要照着去点。

**「安装 / 卸载」改成「启用 / 关闭」。** 它本来就配不上安装和卸载这两个说法——没有下载，没有文件落盘，翻的只是一个开关。

**总开关要重新盘一遍。** 现在的规矩是「多成员单位的每个成员都要有一个能翻的开关」，这条在拆页之前成立。拆完之后有些页只剩一两个成员，页顶的那排开关和页内的开关说的是同一件事，重复了。要逐页看哪些总开关还有意义，没意义的删掉——这条规矩本身可能也要跟着改。

### 外观主题：导入 VS Code 配色

**候选方向，尚未实现。** 允许用户导入 VS Code 主题，更换 kururu 内置配色。当前候选版以灰阶为主，先把颜色收成统一的语义角色，再让导入主题替换这些角色，避免每个页面各自取色。保留当前灰阶作为默认主题。

- **T1 · 配色范围。** 覆盖面板与设置页的背景、卡片、文字、边框、强调色，以及监视曲线和核心负载图。只更换颜色，保留章鱼标记的形状、布局、字体与交互。菜单栏图标需继续适应 macOS 的明暗背景。
- **T2 · 导入与映射。** 先核对 VS Code 官方主题格式及实际主题样本，再确定首版支持的文件类型与字段。把可用颜色映射到 kururu 的语义角色，缺失颜色回落到内置主题。代码语法高亮色不直接当成界面颜色，也不承诺完整复刻编辑器外观。只读取主题配色，不安装或运行扩展。
- **T3 · 预览与验收。** 应用前预览监视页和设置页，可恢复默认。检查浅色、深色、低对比度及字段不完整的主题。热压力、警告等状态保留明确的语义与文字标识，避免换色后正常和危急难以区分。导入解析失败时说明原因，保留当前主题。

首版交互与颜色映射表待设计评审后确定，本轮只记录方向。

### 窗口与桌面

```
窗口切换器    留，内部选项多，到时候逐条过
Dock          留（窗口预览 + 点按，已合成一页）
窗口行为      三个并成一页：
              · 绿灯改成最大化，而不是全屏
              · 关掉最后一个窗口时退出 App
              · ⌘Q / ⌘W 需要确认才生效
```

砍掉窗口布局之后这个组只剩三页：**切换器 · Dock · 窗口行为**。

「窗口行为」这个名字管的是**标准窗口控件按下去会发生什么**——交通灯和那两个快捷键。
它和 Dock 的最小化、切换窗口在认知上会有一点重叠，但 Dock 那页管的是「从 Dock 图标操作窗口」，
这页管的是「窗口自己的按钮和快捷键」，边界说得清。

### 输入设备 / 全局入口

分成两组：**输入设备**是鼠标、触控板、键盘（按键防抖 + 文本片段 + Super Key 三个成员合一页）；**全局入口**是键盘快捷键、径向菜单、命令栏——它们装的都是下面已启用的功能，自己没有内容，所以和「功能」「菜单栏图标」「菜单栏面板」一起排在最上面。
**命令栏是重点**——三个入口里它是唯一能搜索的。
快捷面板砍掉，能力并进菜单栏面板的「固定操作」区。

**径向菜单要加触控板手势触发。** 现在只能用快捷键和鼠标键唤起，触控板用户没有顺手的入口。这条在上游提过 issue。

**「触控板」页体量不够**，现在整页只有三指中键一项。今后看它能扩成什么——手势、边缘触发这一类，凑不出一页就并回鼠标。

### 剪贴板与文件

剪贴板页收三样：历史、纯文本粘贴、清理 URL。
访达快捷键留（剪切粘贴 + 重命名）。
**新增：访达自动整理**——往文件夹里加文件图标不自动对齐，每次都要右键整理。注意文案：macOS 的「整理」是一次性对齐，「整理方式」才是持续按规则排，我们要的是后者的效果。
草稿板降级成「便条」，改名，做成可 pin 的临时便条或灵动岛的小功能。

### 捕获与内容处理

屏幕捕捉（截图 + OCR + 颜色吸管）、媒体（压缩视频图片 GIF）留。
**OCR 的打法：吃「快」，不吃「全」。** 一个快捷键，框一下，字进剪贴板，不弹窗不打断。对手是 TextSniper 和 Shottr 那一档，不是 CleanShot X。
**媒体今后加 PDF。** 转换、压缩、合并这一类，和现在的图片视频处理是同一条流水线。

**屏幕录制留，整个留。**（推翻了原先「只留 GIF、砍编辑器」的决定——那条的前提是「我们做的是半成品」，去读了代码之后发现不成立。）

这个品类真正值钱的活它已经在做了：`RecorderMotion` 656 行做的是点击时画面探进去、指针滑行而不抖，而且是离线算的——录完了才算，所以能同时看过去和未来，不像实时滤镜要拿延迟换平滑。再加上光标图库、背景和圆角、模糊区域、文字和图片叠加、打字轨迹。这些正是 Screen Studio 卖钱的东西。

砍掉的只有**临时链接**：把录屏传到服务器换一个 1 小时 / 6 小时的链接。那是别人替用户保管他的屏幕，归到下面第三类。

### 声音与设备

音量混音器（含输出切换）、麦克风静音、阻止 Music 都留。
**混音器是留得最理直气壮的一个**：Windows 2006 年就有，2026 年 macOS 还是只有一个总音量，苹果没有任何要做的迹象。

**「阻止 Music」今后扩成「App 拦截」。** 现在只拦一个 Music，体量配不上一整页。改成一张用户自己维护的名单：媒体键误触起 Music、按了某个键弹出「词典」、诸如此类，谁烦谁进名单。我们只预置 Music 一条，其余用户自行追加。

**「静音麦克风」体量也不够**，现在就是一个开关加一个菜单栏指示。今后看它能整合扩充成什么——和输入设备状态、和会议场景相关的一组功能，而不是单独一页。

### App 管理

清理、卸载器留。

**新增：已装的包（只读）。**

两条判据合起来划出边界：

```
包列表     列「你选择装的」，而且列给「看不见依赖关系」的人
清理器     列「自己长出来的」——没人主动装、没人知道存在、没人清
```

| 来源 | 怎么读 | 怎么分 |
|---|---|---|
| brew | `brew info --json=v2 --installed` | 每个包自带 `installed_on_request` 标记 |
| brew cask | `brew list --cask` | 全是主动装的 |
| mas | `mas list` | App Store，无依赖概念 |

brew 和 mas 是 Mac 上装东西的默认方式。brew 半技术用户也在用（照着教程粘一行就装了），
而**「哪些是依赖带进来的」正是他们看不见的东西**——列表里 `openssl@3` 有新版，
其实是 ffmpeg 拖进来的，跟着升容易炸环境。

**升级按钮只给主动装的那些。** 依赖不给 —— 它跟着需要它的包一起升，单独给按钮等于把这层关系藏起来。

**已完成**（`feat(packages)`，净 −2344 行）：搜索和安装整个删掉，菜单栏面板那块也删掉；
卸载只从卸载器进（brew 装的 app 被卸载时要同步 brew 的记录）。

### 新增：全局环境（单开一页，只读）

放 App 管理下面自己一页。**不是列包，是让人看懂自己的环境长什么样。**

这一页的受众和包列表不同，也正是它的理由：普通用户不会打包管理器命令，
但会装 Cursor、粘一段 MCP 配置，然后卡在环境问题上——**他们被它坑，却完全看不见它。**

#### 四块内容

```
1  谁在赢
   node / npm / npx / python / bun 各自解析到哪个文件，版本多少
   同一个命令有几份，PATH 顺序决定了谁赢

2  哪些是 shim
   命令名骗人。显示：它是壳 → 真正执行的是谁 → 行为会有什么不同
   这是「npm 和 bun 混在一起」的根，比列包重要

3  GUI app 的 PATH ≠ 终端的 PATH
   并排显示两串，标出「终端有、GUI 没有」的那些
   一句话说清后果：从访达启动的 app 找不到这些命令
   ← 直接回答「MCP 配好了为什么起不来」，社区问一百遍的那个

4  缓存占了多少
   npx / bunx / node_modules，只报大小；清理动作在清理器
```

再给一个**「复制诊断报告」**按钮——去 issue 区求助时贴这个，比来回问十轮快。

#### 本项目开发机上的实测（这就是要显示的东西）

```
node 有两份，版本还不一样
  /usr/local/bin/node        真 node   v24.16.0
  ~/.local/bin/node          shim→bun  报 v26.3.0     ← PATH 里赢的是这个

npm / npx 都是 shim
  npm  → 转给 bun 的脚本，注释写着 never falls back to Node
  npx  → 直接 exec bunx

launchctl getenv PATH 为空
  → 访达/程序坞启动的 app 拿到的是 launchd 默认 PATH
    ~/.local/bin、~/.bun/bin、/opt/homebrew/bin 都不在里面

PATH 里还有 /opt/anaconda3/condabin
bunx 缓存 2.3 GB
```

终端里 `node -v` 说 26.3.0（其实是 bun），真 node 24.16.0 躺在旁边没人用。
一个包说「需要 node 20+」，用户根本判断不了自己满不满足。

#### 能做的动作

**复制绝对路径**——这一页最有用的按钮。

```
npx    ~/.local/bin/npx        [复制]
node   ~/.local/bin/node       [复制]
bun    ~/.bun/bin/bun          [复制]
```

用户真正要解决的是「Claude Desktop 找不到 npx」。正解**不是**给全系统改 PATH，
是在那个 app 的配置里写绝对路径。一次点击解决社区问一百遍的问题，零风险。

**复制诊断报告**——去 issue 区求助时贴这个，比来回问十轮快。

#### PATH 只能管一半，另一半不该假装能管

```
终端 PATH     能管。写 /etc/paths.d/cairn —— 我们自己的一个文件，一行一个路径。
              没有语法可错，删文件就撤销，要一次管理员授权。
              这是苹果给的正规位置，homebrew 自己就在用（/etc/paths.d/homebrew）。

              限制：path_helper 是把它追加在系统路径后面的，
              所以能让一个命令「被找到」，不能让某个 node「抢在别人前面」。

              绝不碰用户的 shell 配置。本项目开发机上 PATH 散在四个文件里改了 15 处
              （.zshenv 4、.zprofile 2、.zshrc 4、.bash_profile 5），
              我们再插一脚只会让以后排查更难。

GUI app PATH  改不了，也不该假装能改。
              launchctl setenv 要重启 app、重启电脑就没了、
              「登录时重开窗口」还会绕过它。
              这半靠上面那个「复制绝对路径」解决。
```


**已完成**（`feat(environment)`，+1057 行）：四块内容加两个复制按钮都在，落在 App 管理下自己一页。
终端 PATH 由用户自己的登录 shell 答（只有 shell 答得了），不读也不写他的配置文件；
不常驻，打开这页才查一次，每条命令都带超时。

**没做：写 `/etc/paths.d/cairn`。** 它要一次管理员授权，而且只能让命令「被找到」、不能让它抢在前面，
和这页的「读」是两件事，单独做。

#### 为什么这页取代了「列 npm 包」

```
列 npm 包    只有开发者装的东西，而开发者有终端        受众错了
全局环境      普通用户被它坑，但完全看不见它            受众对了
```

#### node 的东西全部归清理器，不进包列表

一度想列 npm 全局包，理由是「普通 AI 用户在用 npm」。这句话不成立：

```
会跑 npm i -g 的人      在终端里打字的人——和 pip、cargo 同一批，
                        他们有终端，不需要我们代劳

普通 AI 用户干的事      装 Claude Desktop / Cursor，粘一段 MCP 配置，
                        里面是 npx -y @some/server
                        从头到尾没打过任何包管理器命令
```

**`npx` 不做全局安装**，东西落进缓存，全局目录里什么都没有。
所以「列 npm 全局包」列出来的恰恰只有开发者装的那些，正中「用的人自己就有终端」这一条。

普通用户真正产生的是**缓存**——那不是「已装的包」，是垃圾，归清理器：

```
~/.npm/_npx/              npx 缓存
~/.bun/install/cache      bunx 缓存   ← 本项目开发机上 2.3 GB
node_modules 缓存          各处
```

清理器扫这些目录时有个坑要记着：**命令名会被 shim 掉，目录不会**（细节见上面的「全局环境」）。
任何靠调命令定位缓存的写法，在装了 shim 的机器上都会失败。

### 端口

**一次性查询，不做常驻。** 命令栏输入端口号 → 谁占着 → 可结束。
场景已经不只是开发者：跑本地 AI 会开一堆 localhost 端口。
已知限制：不给 root 只看得到自己用户的进程。先做无 root 版。

## Not Do

这一节是判据，不是清单。**一个功能被砍，通常是因为它属于下面某一类，而不是因为它单独不好。**

### 一、苹果已经做了

做了等于用户装两份同样的东西，还得记住哪个在生效。

```
内置屏亮度            苹果键盘上那两个键就是干这个的
防止睡眠（接电源）     系统设置 → 电池 → 选项里有
窗口二分 / 四分        macOS 26 自带
```

注意边界：苹果做了**一部分**不等于整件事都被覆盖。保持唤醒留下来，是因为电池模式、定时、合盖不睡苹果都没给。判断的时候要问「苹果覆盖的是哪一半」。

### 二、这是一整个独立软件的品类

菜单栏工具做不好，也不该做。

```

Markdown 编辑器   草稿板往这个方向长就是另一个产品。（我自己有 Markpad）

窗口管理          27 种摆法是 Rectangle / Magnet 的赛道，它们免费且更成熟。
                  笔记本上窗口空间本来就不大，真正用得上的是超大屏用户，
                  而那批人已经在用专门的工具。
```



### 三、需要私有 API、长驻后台进程、或保管用户凭据

这三条是硬线，踩到就不做。

```
私有 API      靠没文档的行为撑功能，系统一升级就碎，而且我们无法保证
长驻后台      为一个功能常驻一个进程，所有用户替这个功能付电和内存
托管凭据      用户的云盘密钥、SSH 密钥交给我们保管，一旦出事没法收场
```

被这条挡住的：把 Dock 锁在某个显示器（无 API）、罗技鼠标专属键（要私有 HID）、
端口转发和 SSH 隧道（长驻 + 凭据）、录屏上传到用户自己的云（凭据）。

端口查询能做，正是因为它查完就退，不常驻。

### 四、绕过了别人的安全机制

```
App 更新      各家 App 自己的更新通道有灰度分批。我们统一推，等于把那道拦截绕掉了。
              而且常用的 App 用户自己会更新，不常用的本来就不用更新。

Homebrew 依赖升级  brew 里一大半是依赖包（别的包拖进来的），用户不知道哪个是哪个。
                  在列表里看到 openssl@3 有新版就点升级，那是 ffmpeg 拖进来的，
                  升了容易炸环境。
```

这两条不是「功能不好」，是**我们的界面会诱导用户做错事**。App 更新整条去掉；
brew 这条**改成按 `installed_on_request` 分**：主动装的给升级按钮，依赖不给。
判据变了 —— 原来说「用户不知道哪个是哪个」，现在我们知道了，就告诉他。
残留的风险：`brew upgrade <包>` 仍会连带升它的依赖，日志里能看到。

### 五、它想省的那一步本来就不费劲

```
DMG 安装器    用户得先打开我们的安装器；拖拽式和安装包式事先分不清；
              也没法选装到哪。双击 dmg 拖一下再删掉，本来就不麻烦。
```

### 六、权限成本高过收益

```
相机预览      为了「开会前看看自己」，要用户把摄像头权限交给一个菜单栏工具。
              而开会软件自己就有预览。
```

### 七、同一件事已经有了入口

```
快捷面板      它那 27 个动作，命令栏一个不少，径向菜单也全放得下。
              它唯一独有的是「不用配置、点菜单栏就有」——而面板本来就要做
              「固定操作」区，那块就是它。
              三个入口各司其职：命令栏管搜索，径向菜单管鼠标，面板管常用。

结束进程      监视本来就在列谁吃 CPU/内存，右键结束是顺手的事，
              不需要一个独立的窗口和一页设置。
```

### 八、用的人自己就有终端

这一类不是「功能不好」，是**受众搞反了**。

```
Python 全家       pip、uv、conda、miniforge、venv……Python 的环境本来就是散的，
                  同一台机器上好几套并存。要列就得先列环境，列环境就要跨语言列，
                  摊子一下铺开。
                  而且但凡用到这些的基本都懂点开发——他们有终端，
                  不需要我们代为查看，更不需要我们代为升级。

npm / bun         作为「包管理器」都不列——会跑 `npm i -g` 的是终端用户。
                  普通 AI 用户走的是 `npx`，那不产生全局安装，只产生缓存，
                  而缓存归清理器。**列的是「东西在哪」，不是「你用什么工具」。**

cargo             Rust 开发者，同理。
                  （`cargo install --list` 能正确排除 rustup 工具链，
                  所以技术上不是问题，是受众问题。）

gem               机器上那份是系统自带的，动它有风险。
```

对照着看为什么 **npm 留下**：现在大量普通 AI 用户在用 `npx` 跑 MCP 服务、
用 `npm i -g` 装 CLI 工具。他们装完不知道装了什么、装在哪、怎么删——**正是需要有人列给他们看的那批人。**

同一条判据，一个砍一个留。

### 九、测不了

```
超亮度        把亮度推到苹果标称值以上，本来就在标准外，偏色风险真实存在，
              而且我们没有设备验证。做一个自己没法验证的功能，等于把风险
              转嫁给用户。
```
